# ADR-001: Adopt Hex Layered Architecture

**Date:** 2026-04-15
**Status:** Accepted
**Author:** Claude

## Context

The forward-mcp codebase currently lacks hex layered architecture. All code is organized in a flat `internal/service/` package that mixes:
- Domain logic (business rules)
- Port interfaces (abstractions)
- Adapters (implementations)
- Use cases (orchestration)

This violates clean architecture principles and makes the codebase harder to test, maintain, and extend.

## Decision

We will adopt hex (ports & adapters) layered architecture with the following structure:

```
internal/
├── domain/           # Business entities and rules (no external dependencies)
│   ├── entities/     # Core domain models
│   └── services/     # Domain services
├── ports/           # Interfaces defining how the domain interacts with outside world
│   ├── cache.go      # CachePort interface
│   ├── database.go  # DatabasePort interface
│   ├── client.go    # APIClientPort interface
│   └── memory.go    # MemoryPort interface
├── usecases/        # Application services / orchestration
│   ├── query_service.go
│   ├── cache_service.go
│   └── memory_service.go
└── adapters/        # Implementations of ports
    ├── cache/       # SemanticCache, BloomSearch
    ├── database/    # SQLite implementations
    ├── client/     # Forward API client
    └── memory/      # Memory system implementation
```

## Consequences

**Benefits:**
- Clear separation of concerns
- Easier unit testing via port interfaces
- Flexibility to swap implementations (e.g., Redis for cache)
- Better testability of domain logic in isolation
- Improved code navigation and discoverability

**Risks:**
- Requires refactoring ~30 files
- Potential runtime regressions
- Learning curve for contributors unfamiliar with hex architecture

## Migration Plan

1. Extract domain entities first (lowest dependency)
2. Define port interfaces based on existing service signatures
3. Move adapters to new package
4. Refactor usecases to depend on ports, not concrete implementations
5. Add integration tests for each layer
